# Whole-game coverage

**Goal:** the whole game recompiled and running without stops, found by work that does not depend on someone steering the game to each state. Decided by the user on 2026-10-18: playing or scripting button input to find what is missing does not scale (too many states, different buttons in each). This plan goes ahead of the [performance plan](PERFORMANCE_PLAN.md).

**The user's decisions:** an EE interpreter is accepted as a logged bridge for code the map does not hold yet (compiled natively at the next build); a tool-only starter of game states is accepted (never in the player programs); exhaustive sweeps are the final validation, not the work now (2026-10-19).

References consulted (BT3-Recomp's interpreter and orchestrator, Tenkaichi3Decomp's headless starter and per-blank state hash): [reference architecture](../../reference/REFERENCE_ARCHITECTURE.md#whole-game-coverage-2026-10-18).

## Step 5: what is left

From the census (2026-10-18): 163 runtime conditions on guest PCs, stack offsets, call counts or startup phases; of the 69 system calls the code reaches, 5 handled only under a gate and 19 not at all (thread exit and deletion, interrupt-context forms, exception handler setup, leaving the game, `GetMemorySize`, three unnamed numbers). Most are startup replays that work as they are; they are made general group by group in the [runtime generalization plan](RUNTIME_GENERALIZATION_PLAN.md) (2026-10-19: kernel semaphores, the GS reset path and threads done, 108 lines left; groups 4 to 6, the startup's own replays, wait until after the final validation, the user's decision of 2026-10-20). The unhandled thread calls are reached only through thread teardown (the sound library's shutdown at `0x315248`, a worker's exit at `0x31EB88`).

## Step 6: what is left

- **New Game's state — done 2026-10-19:** the save data is a 16 KB block at the pointer `0x387F2C` (`gp-0x3EC4`; `0x631000`). Its Z-item records are 4 bytes each from `+0x1F30` (flags: 1 owned, 2 new; then the count); `0x298460` gives an item. The title's New Game (`0x3B9D58`) resets the block (`0x2982E8`) and gives the starting items from a table in the title's resources. The starters now run it the game's way: load the menus' package as the entry does, the title's setup (`0x3B84B8`, argument 2), New Game, the title's release (`0x3B8C78`), free the package. With a card folder that holds a BT2 save, the starter then copies the save file into the block (the game's load leaves the block equal to the file, checked byte for byte). The Evolution Z hang is gone; the explorer runs every screen without a stop.
- **Item Fusion (the user: characters are unlocked by Z-item fusion) — checked 2026-10-19:** with the user's save, Evolution Z's third entry is Item Fusion. The recipes are a 97-entry table the fusion screen loads (item, item, result; `0x3D88A8` looks a pair up and refuses it when the result is already at its maximum). Fusing two Support items (Abandonment Essence + Hit Essence) gave Master's Essence with the game's own dialogue and animation; a character item (Zarbon + Unsealed → item 450, on a copy of the save without 450) left item 450 owned and new, the used item gone, one Zeni less. A wrong pair gets "That combination is no good". The explorer does not find fusions by itself (see below).
- **Special sagas (the user) — found 2026-10-19:** sagas are Z-items 390 to 414 (one per episode), given as a story battle's reward items; in a battle the story lets the player lose (rule 3) only a win gives them. Episode 0 part 0's win gave item 411 (episode 21) without input ([story mode plan](STORY_MODE_PLAN.md), "Battle rules, rewards and sagas").
- **Battle content (the user, 2026-10-19):** stage objects take damage and break in CPU battles (7 of 16 stages each); a story battle places the first Dragon Ball the player lacks, which appears when an object that can hold it breaks and counts when the player's side picks it up (same section of the story plan).
- **The other screens' battles — run 2026-10-19:** the screen starter gives both sides of a battle to the CPU and, before each battle, gives side 0's fighters at least side 1's CPU level (fighter record word 2) and strength values (words 5 to 12), which the modes set above the player's; it reports each battle's kind, rule and result (`starter_mode_battles`). With cross pressed every 120 fields: Ultimate Battle Z (battle kind 2) went through its first course's fights (8 battles in 40,000 flips, 3 won in a row, then a stronger opponent and retries; 4,453 functions), Dragon Tournament (kind 3) to "Champion" and its save question (4,197 functions), nothing interpreted. Ultimate Training (kind 4, rule 4) stayed in its first lesson: a lesson waits for the player to do what it shows, which the CPU does not.
- **Ultimate Training's lessons — run 2026-10-20:** 21 lessons (progress structure `+0x484`; the lesson menu, overlay `0x3EFE18`, writes its scroll position plus cursor there on cross). A lesson shows its explanation pages and a scene, then a practice battle with side 0 under the pad (the lesson setup passes control 0 for it; the screen starter now leaves it so in mode 61). Each action a lesson asks for reports a task bit to `0x211418` from the fighter's action states (Movement bit 0 from state 7's entry `0x2282B8`, Dash bit 1 from `0x22A5D0`, Lock on bit 2 from `0x224B30`, the other lessons' bits 3 to 28 from their states); the report counts only in a practice (fighter word `+0x2B0` bit `0x400000`). When the fighter's done bits (`+0x1468`) equal the lesson's mask (21 words at `0x36FA10`: lesson 0 `0x7`, 1 `0x38`, …, 20 `0x10000000`) the game sets `+0x1465`, which the battle's end (`0x1F8760`) turns into a result bit; the practice ends with the pause menu's Exit training (Pause → Exit training → Yes sets the result's bit 8), and the lesson's closing pages lead back to the menu. The pause's Practice Check lists the lesson's tasks and controls (text `0x63 + lesson + 1`). Scripted input reaches Movement (down) and Dash (direction and cross); Lock on needs the opponent out of sight first. For coverage the screen starter takes the lessons in turn, reports a lesson's whole mask at its practice's first report (or after about 600 frames of practice), so the game clears it by its own path, and ends the practice as Exit training does (tool runs only). `tools/ps2recomp/screen_run.py --modes 61 --flips 90000 --down-every 400` ran all 21 lessons and began the list again (3,235 functions entered, 2,467 before; nothing interpreted); the same tool reran Ultimate Battle Z and the Dragon Tournament as before.
- **Ultimate Battle Z's courses — run 2026-10-20:** 15 courses (Kakarot Road to Unlimited; the course table, 56 bytes a course, comes with the screen's files) of 1 to 9 battles, some with a battle condition (team battles as Ginyu Force: rule 2, one fighter against five). A course opens when the courses it needs are cleared: `0x24B598` checks the save block's cleared byte per course (`+0x2C0`, the level it was cleared on) by the course's unlock kind (word 0: 0 always; 1 course 0; 2 courses 1 and 2; 3 course 3; 4 courses 4 and 5; 5 courses 7 and 8; 6 courses 9 and 10; 7 course 11; 8 course 12; 9 all of 0 to 13), so every course needs only lower-numbered ones. Course Select (overlay `0x3F5F00`) lists the open courses with the cursor on the last course chosen (progress `+0x64`); the best points are kept per course and level from save `+0x20E`. After a cleared course the screen runs its own copy of the story's save flow (`0x3FE450`, state word at `*0x42A58C + 0x50`, 21 is "Exit saving?"; the Dragon Tournament's copy is `0x3CEF10`, `*0x42311C + 0x150`). For coverage the screen starter puts Course Select's cursor on the first course not cleared, gives side 1's fighters one health bar between them (fighter record words 17 and 18, 10,000 a bar) and side 0 the highest CPU level and strength of side 1's fighters, and answers "Exit saving?" with Yes (tool runs only; no tool run saves). `screen_run.py --modes 10,24 --flips 600000`: all 15 courses cleared in order (175 battles, 6 lost and retried, then Kakarot Road again; 5,191 functions entered, 4,336 before), and the Dragon Tournament past its save question through repeated tournaments (130 matches; 4,634 functions, 4,197 before); nothing interpreted.
- **Fusions found by the explorer itself — dropped 2026-10-19:** a fusion takes about 20 exact presses, beyond a breadth-first search over buttons; the scripted fusions above already ran the fusion code.

## Step 6: BT2's state machinery (the starters rely on it)

- **Main loop** (`0x100680`): load the overlay, call its entry `0x3B7FA8` (title and menus); when it returns, run `0x2A8A38` (story) if progress flag `0x200` is set, else the battle routine `0x103000`.
- **Progress structure** (pointer at `0x3876A4`): flags `+0x18` (`0x40` first run), mode `+0x1C` (modes 1 to 64, table `0x421950`), story episode `+48` and part `+52`. The main menu's ten entries set modes 6/7 (Dragon Adventure), 10, 24, 30 (Dueling), 61, 53, 5, 38, 48, 43 (table `0x4217B0`).
- **The entry's first run** that later states need: mount the second archive (`0x100950(1)`, wait `0x100990(1)`; files from 13,234 up) and load the common files (`0x102450`; the character table among them). The card check, logos and films are skipped by the starters.
- **Battle setup** (system structure, pointer at `0x3876A0`): `0x101A10` clears it; `0x101A60(kind, music, …, stage)` (kind 0 versus, 6 demo; the stage passes through `0x24AF50`); `0x101AB0(side, …)` sets control (byte `+452`: 1 CPU); `0x101AF8` a fighter (character × 9 + variant). The title's demo picker `0x3B9710` makes the same calls from a 21-entry table.
- **Ranges:** characters 0 to 129; stages 0 to 15 (from 16 the game shows Wasteland); variants 0 to 8 (not every character has all).

## Limits

- The interpreter runs only code the map does not hold; it is not a fallback for refused requests, and a gate run that interprets anything fails.
- No fixed game addresses in general handlers; the starters are the one place that writes the game's own fields, in tool runs only.
- Sweep results, pictures and address notes stay in ignored `work/`; documents record counts and descriptions only.
- A new subsystem reached by a sweep (such as the story script machine) gets its own plan before work on it.
