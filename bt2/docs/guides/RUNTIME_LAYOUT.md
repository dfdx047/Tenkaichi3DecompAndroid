# Runtime source layout

`runtime/` holds the handwritten compatibility layer: the code that runs the generated BT2 functions and the native services that answer their IOP requests. Generated code is never stored here. It stays in the ignored `game/generated/` and `work/` folders.

## Folders

| Folder | Responsibility |
| --- | --- |
| `ee/` | EE runtime used by generated code. `ps2_runtime.h` is all that generated code sees: the CPU context and `PS2Runtime`, the entry points it calls. `ee_runtime.h` holds `EeRuntime`, the full runtime (state and small helpers), which derives from `PS2Runtime`; `guest_interface.cpp` forwards each entry point to it. The implementation is split into `ps2_runtime_syscalls.cpp` (syscall and SIF RPC dispatch), `ps2_runtime_memory.cpp` (guest memory and memory-mapped I/O), `ps2_runtime_services.cpp` (owned SIF/RPC service handlers), `ee_gs_readback.cpp` (the GS readback register sequence: VIF1 normal-mode DMA, FIFO and bus direction), `ee_gs_privileged.cpp` (the GS library's reset path: CSR reset and read, the interrupt mask, SetGsCrt) and `ps2_runtime_dispatch.cpp` (guest calls, interior entries and kernel binding). `state_hash.*` hashes the guest memories at every field for comparing runs (`BT2_STATE_HASH`). `game_patches.*` holds the player's optional patches of the executable (widescreen), written after it is loaded. `ee_interpreter.cpp` is the interpreter bridge for code no generated function holds, with its handler table described in `ee_interpreter_handlers.h` (the handlers are generated; `probe/interpreter_handlers_none.cpp` stands in without them). Thread scheduling (thread syscalls, workers on retained stacks, main sleep/wake) is in `ee_thread_scheduler.cpp`, with the worker execution owner in `ee_execution_owner.h`. The folder also has the FPU, the retained EE stack, logical timers, startup checkpoints, the native IPU (`ipu_device.*`: registers, commands and fromIPU output; `ipu_input.*`: toIPU DMA, input FIFO and bit pointer; `ipu_vlc.*`: VDEC header codes; `ipu_block.*`: BDEC macroblock decoding; `ipu_csc.*`: colour conversion), the DMA source-chain walker (`dma_chain.*`), VU0 macro-mode support (`vu0_macro.cpp`: VU0 data memory instructions, status flags, VPU_STAT) and stopped DMA channels (`stopped_dma_channels.h`: channel registers retained, starts refused unless an owner models them, as scratchpad DMA does). |
| `vu/` | The 3D pipeline behind VIF1 DMA ([plan](../plans/graphics/VU1_PIPELINE_PLAN.md)): the VIF1 code interpreter (`vif1.*`: registers, UNPACK, MPG, microprogram starts, DIRECT) and VU1 (`vu1.*`: data and microprogram memory, the microprogram interpreter, XGKICK packets; `vu1_handwritten_registry.cpp` and the files it names: the game's heaviest microprograms written by hand as native code, chosen by program key). No dependency on the EE runtime; `EeRuntime` owns one `Vif1` and feeds it the words of each VIF1 transfer. Also the key of the program a start runs (`vu1_program.h`), the SSE helpers shared with translated code (`vu1_simd.h`) and the stand-in for builds without native translations (`vu1_native_none.cpp`). |
| `gs/` | GIF/VIF1 feeders shared by both renderers: GIF DMA staging and the startup texture/VIF checkpoints. |
| `gs/cpu/` | The GS command sink (`gs_command_sink.*`): checks the GIF data, follows the GS registers, local->host transfers and FINISH, hands accepted data to the GPU renderer and feeds the texture names in step with it; keeps no GS memory and draws nothing (the CPU renderer was removed 2026-10-21). Its GS layout functions are the texture names' reference. |
| `gs/gpu/` | paraLLEl-GS backend (`gpu_gs_backend.*`), mirror/GPU-only driver (`gpu_gs_mirror.*`), HD texture packs (`hd_texture_pack.*`) the window presenter (`gpu_window_presenter.*`: a swapchain on the viewer window, behind `host/window_presenter.h`) and the in-between pictures of 60 fps battles (`in_between_frames.*`: a second renderer drawing from the game's recorded commands, with `vu/vif1_blend.*`), built with `BT2_GPU_GS`. |
| `gs/textures/` | PCSX2-compatible texture names for HD texture packs (`gs_texture_names.*`: its own copy of GS memory and the CLUT, fed by the command sink when `BT2_TEXTURE_NAMES` is set). |
| `host/` | Host presentation: decoding the displayed framebuffer, the live viewer window, for the mixed audio the WAV writer and the audio device (waveOut), and host input: keyboard, XInput and DualSense readers (`host_input.h`, `dualsense_report.h`), the neutral gamepad state (`gamepad.h`) and the mapping to the game's controller (`input_mapping.h`); the frame pacer (`frame_pacer.h`) and the sampling profiler (`sample_profiler.h`). The player's side: the settings file (`settings.h`), the menu model, input and renderer (`menu_model.h`, `menu_input.h`, `menu_renderer.h`), the menu loop with the shared settings screens (`menu_host.h`), the launcher (`launcher.h`), the in-game menu (`overlay.h`) and a player's run inside the runtime (`player_session.h`). |
| `game/` | The player's programs `bt2-game` and `bt2-launcher` (`game_main.cpp`): settings, launcher, then the runtime program as a child process. No game code. |
| `services/` | Native SIF RPC services that replace the IOP ([plan](../plans/iop/NATIVE_SERVICES_PLAN.md)); no IOP code runs. The generic SIF RPC layer (`sif_rpc.*`), one file per service (disc, FILEIO, memory card, controller, IOP heap and uploads, LOADFILE, sound driver and SOUNDS, CRI ADX), the CRI stream buffers and audio flow (`cri_stream.h`, `cri_audio.h`), the IOP heap (`iop_heap.h`), the pad block layout (`pad_block.h`), and `devices/`: ISO metadata and sector reads, and the DualShock 2 with its deterministic input script (`pad_script.h`). Sound output: the stream mixer (`audio_mixer.h`) and the effects sampler (`sound_sampler.h`, with `sound_bank.h` and `spu_adpcm.h`). |
| `probe/` | Executables. `entry_probe.cpp` runs the startup checkpoint in stages, each in its own file: evidence inputs, generated-code bindings, checkpoint checks and reports, sharing `probe_state.h`. The selection loop's entries are bound in `selected_bindings.cpp` and `overlay_bindings.cpp`, so a new selection recompiles only those small files. `game_starter.cpp` is the tool-only `BT2_START_BATTLE` and `BT2_START_SCREEN` (a battle or a screen without input). The folder also has the generated-code and RPC-bind probes. |
| `tests/` | Unit and subsystem tests registered with CTest. |

`main.cpp` is the plain host executable (`bt2-port`).

## Conventions

- **Includes:** handwritten code includes headers from another folder by their path from `runtime/`, for example `#include "gs/cpu/gs_command_sink.h"`. Headers in the same folder are included by name. Generated code includes `ps2_runtime.h` by name, through the `runtime/ee` include directory; handwritten code includes `ee/ee_runtime.h`.
- **Headers reached by generated code** (`ps2_runtime.h`, `ps2_runtime_macros.h`, `ps2_fpu.h`): keep these to the CPU context and the entry points generated code calls. An edit to one of them recompiles every generated unit. Runtime state belongs in `ee_runtime.h`, which generated code never includes, and implementation in the folder's `.cpp` files. To give generated code a new entry point, declare it in `PS2Runtime`, implement it in `EeRuntime` and forward it in `guest_interface.cpp`.
- **Build targets:** the handwritten runtime is built once as the `bt2-ee-runtime` library and linked by every probe and test. Its hot sources (`BT2_EE_HOT_SOURCES` in `CMakeLists.txt`) and the generated code (`bt2-entry-generated`) are compiled optimized in Debug too.
- **New code:** a new subsystem or service gets its own file in the matching folder. Add the file to the corresponding source list in `CMakeLists.txt`:
  - `BT2_EE_RUNTIME_SOURCES` (EE runtime and native services).
  - `BT2_EE_HOT_SOURCES` (interpreters and other hot loops: FPU, GS model, IPU, VIF1/VU1).
